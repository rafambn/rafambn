COMPOSIÇÃO

Use uma vista ortográfica de cima, perpendicular ao solo. Desenhe o navio, o mar, o cais e os contêineres nessa mesma perspectiva, com o texto orientado para leitura normal.

Um único navio cargueiro fica na lateral esquerda, com seu comprimento orientado verticalmente. Os seis projetos ficam à direita, no cais. Cada seção apresenta um contêiner visto de cima, com o nome do projeto sobre seu teto, estrelas e visualizações. A área inteira de cada projeto funciona como link para seu repositório.

No desktop, o grid tem TRÊS LINHAS e DUAS COLUNAS:

Navio à esquerda | KMaP       | FrameBar
                 | KFlate     | KeyManager
                 | Scribe     | wg-kotlin

No mobile, o grid tem SEIS LINHAS e UMA COLUNA:

Navio à esquerda | KMaP
                 | FrameBar
                 | KFlate
                 | KeyManager
                 | Scribe
                 | wg-kotlin

O navio permanece à esquerda também no mobile. Reserve espaço para que os nomes e números sejam legíveis em uma tela estreita. Adapte as proporções, a quantidade de elementos decorativos e o comprimento do navio à composição de cada formato. Planeje o mobile desde o início. O resultado deve funcionar a partir de 320 px, com rolagem vertical e sem rolagem horizontal.

Crie a paleta, a tipografia, as formas e os detalhes do porto com liberdade. Escolha detalhes que reforcem o cenário e preservem a leitura dos projetos. Dê ao nome e à frase uma posição clara e mostre também as visualizações do perfil: Today, Week, Month e Total.

SVG E DIVISÃO DO CENÁRIO

Toda a arte deve ser SVG vetorial criado em código, com formas, paths, padrões e símbolos reutilizáveis. Construa um desenho viável de manter e leve para carregar. A estética deve parecer um trabalho vetorial intencional.

O cenário precisa ser dividido em partes para permitir links independentes no README do GitHub. Planeje as fronteiras e os encaixes: quando as partes forem exibidas juntas, devem formar o porto com alinhamento consistente. Cada imagem correspondente a um projeto deve estar dentro de um link para o respectivo repositório.

No site, os projetos devem responder ao clique, ao toque e ao teclado. No README, o GitHub exibe SVG como imagem, portanto os links precisam envolver as imagens no Markdown ou HTML aceito pelo GitHub. Verifique quais mecanismos de layout e adaptação o GitHub realmente suporta e implemente uma composição que funcione nesse ambiente. O site deve cumprir exatamente os dois grids descritos. Documente qualquer limitação real do README e a solução escolhida.

DADOS E SERVIDOR

Use a estrutura Kotlin/Ktor deste repositório e preserve a persistência existente dos contadores. Consulte a lista de projetos e as classes de contadores e estrelas antes de integrar o desenho.

Mostre estrelas reais dos repositórios a partir do cache da API do GitHub. Mostre as visualizações persistidas pelo servidor, deixando claro na documentação o que cada contador mede. Os períodos do perfil são dia atual, últimos sete dias, últimos trinta dias e total.

Separe a leitura dos dados do registro de acessos. Pré-visualizações e consultas de estatísticas apenas leem os valores. Defina como as imagens públicas registram acessos, evitando que carregar vários recortes conte uma única exibição como várias visitas do perfil. Preserve as chaves e os dados existentes. Trate falhas da API mantendo os valores disponíveis e usando um estado discreto quando ainda não houver dados.
